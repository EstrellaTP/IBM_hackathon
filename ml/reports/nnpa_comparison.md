# Inference with and without the IBM Z Integrated Accelerator for AI (NNPA)

Generated by `python3 -m ml.models.nnpa_comparison` on `s390x` (IBM z17, z/VM guest, 3 vCPUs). Model: LightGBM trained on the real NHANES features (7965 people, 12 features, 300 trees). Single-threaded scoring; median of repeated calls after warm-up. Engines: LightGBM CPU, IBM Snap ML compressed trees (CPU) and IBM Snap ML zDNN tensors (NNPA).

## Interpretation

- **The NNPA path is real.** With `ZDNN_LOGLEVEL=debug`, Snap ML's `zdnn_tensors` model
  calls `zdnn_matmul_op` on `ZDNN_DLFLOAT16` tensors through the system
  `libzdnn.so.0` (zDNN 1.0.1). The tree format reported by Snap ML is `zdnn_tensors`
  (the script fails otherwise).
- **For this model the accelerator does not pay off.** Our depression model is small
  (12 features, a few hundred shallow trees); converting the input to NNPA tensors costs
  more than the arithmetic it saves. Snap ML on the CPU (compressed trees) is the
  fastest engine at every batch size, 2.3-11x faster than LightGBM's own inference.
- **Same predictions on all engines**: differences to LightGBM of ~3e-8, i.e. the
  float64 -> float32 input conversion. The NNPA's reduced precision only changes a
  tree's branch when a value sits right at a split threshold.
- **What this means for the project.** Inference is not the bottleneck: it takes
  0.3 ms per batch in the latency benchmark (`benchmark.md`). The accelerator becomes
  relevant for heavier models (deep sequence models on raw signal, many patients
  scored in one call); the code path is in place and measured, and the honest result
  is reported rather than assumed.
